# Open WebUI VM for sndbx

## What this machine is

This is a self-contained sndbx virtual machine that runs one self-hosted
[Open WebUI](https://github.com/open-webui/open-webui) instance: a browser UI
for chatting with AI models. It does not run a model server itself; it connects
to external OpenAI- and Ollama-compatible services (for example a self-hosted
model router running on the sndbx host).

The image is based on the official Open WebUI image and adds the sndbx runtime
contract: a dedicated unprivileged `openwebui` account that can be remapped to
the host user, key-only SSH, and a lifecycle hook. All persistent state (the
SQLite database, uploads, caches, and configuration) lives in the host `data/`
directory, bind-mounted at `/app/backend/data`, which is the application home.
Copying `data/` to another checkout moves the whole instance.

The container starts as root, remaps its internal `openwebui` account to
`WEBUI_UID:WEBUI_GID` (default `1000:1000`), repairs ownership of the data
directory, then drops privileges and runs Open WebUI as `openwebui`. Files
created under `data/` therefore belong to the configured user. Point these
variables at the user that runs `sndbx` (`id -u` / `id -g`).

At startup the launcher derives the external service connections from
`EXTERNAL_API_BASE_URL`: the OpenAI-compatible endpoint uses `<base>/v1` and the
Ollama-compatible endpoint uses `<base>`, so the same service can be used
through either of Open WebUI's built-in connection types.

## Default settings and where they live

| Setting | Default | Defined in |
| --- | --- | --- |
| Base image | `ghcr.io/open-webui/open-webui:main` | `Dockerfile` (`OPENWEBUI_IMAGE`) |
| Application home / data dir | `/app/backend/data` | `Dockerfile` (`HOME`); `config.sndbx.json5`, `docker-compose.yml` |
| In-container server port | `8080` (`PORT`) | `Dockerfile`; `WEBUI_PORT` in `.env` |
| Server bind address | `0.0.0.0` | `WEBUI_BIND_HOST` in `.env` |
| Runtime UID / GID | `1000` / `1000` | `.env` (`WEBUI_UID`, `WEBUI_GID`); applied in `docker/entrypoint.sh` |
| Published UI port | host `15080` -> guest `8080` | `.env` (`WEBUI_HOST_PORT`) for Compose; `OPEN_WEBUI_HOST_PORT` in root sndbx `.env`; `config.sndbx.json5` |
| Published SSH port | host `15021` -> guest `22` | `.env` (`WEBUI_SSH_HOST_PORT`) for Compose; `OPEN_WEBUI_SSH_HOST_PORT` in root sndbx `.env`; `config.sndbx.json5` |
| Session signing secret | none (must be set) | `.env` (`WEBUI_SECRET_KEY`); generated by `install.sh` |
| External service base URL | none (must be set) | `.env` (`EXTERNAL_API_BASE_URL`); only in `.env` |
| OpenAI endpoint | `<EXTERNAL_API_BASE_URL>/v1` | derived in `docker/start-open-webui.sh` |
| Ollama endpoint | `<EXTERNAL_API_BASE_URL>` | derived in `docker/start-open-webui.sh` |
| Sandbox memory / CPUs / disk | `4G` / `2` / `20G` | `config.sndbx.json5` |
| SSH user / setup | `openwebui` / via image hook | `config.sndbx.json5` |
| Persistent mount | `data/` -> `/app/backend/data` | `config.sndbx.json5`, `docker-compose.yml` |
| Private env mount | `.env` -> `/app/backend/data/.env` (read-only) | `config.sndbx.json5`, `docker-compose.yml` |
| sndbx envid | `open-webui-env-token` | `config.sndbx.json5` |

### Configuration files

| File | Responsibility |
| --- | --- |
| `Dockerfile` | Base image, sndbx account, SSH policy, runtime defaults. |
| `.env` / `.env.example` | Private runtime identity (`WEBUI_UID`/`WEBUI_GID`), ports, `WEBUI_SECRET_KEY`, and the external service address (`EXTERNAL_API_BASE_URL`, `EXTERNAL_API_KEY`). `.env` is ignored by Git and mounted read-only into the container. |
| `docker/load-open-webui-env.sh` | Loads `.env` inside the container while letting sndbx/Compose deployment values (`WEBUI_BIND_HOST`, `WEBUI_PORT`, `WEBUI_UID`, `WEBUI_GID`) win. |
| `docker/entrypoint.sh` | Applies UID/GID remapping and ownership repair, then starts the app as `openwebui`. |
| `docker/start-open-webui.sh` | Derives the model-provider connections from `EXTERNAL_API_BASE_URL` and starts the server (or `data/config/start.sh`). |
| `data/config/start.sh.example` | Optional startup override (copy to `start.sh` to customize the launch command). |
| `app.py` | sndbx lifecycle hook: ownership repair plus key-only SSH. |
| `docker-compose.yml` | Standalone Docker Compose deployment (mounts, ports, tmpfs). |
| `config.sndbx.json5` | Mergeable sndbx sandbox template. |
| Root sndbx `config.json5` and `.env` | Sandbox registration and optional `OPEN_WEBUI_*` resource and publication overrides. |

## Installing into sndbx

The image source is a standalone repository:
<https://github.com/DenisDx/sndbx_openwebui>.

### 1. Clone it into the sndbx checkout

The directory name must be `open-webui` so it matches `local_image_id`.

```bash
cd "$SNDBX_ROOT/images"
git clone https://github.com/DenisDx/sndbx_openwebui.git open-webui
```

### 2. Create the private environment file

The cloned repository does not contain `.env` (it is ignored). Create it from
the example and set the runtime identity, the secret, and the external service
address:

```bash
cd "$SNDBX_ROOT/images/open-webui"
cp .env.example .env
chmod 600 .env
# Generate a session secret:
sed -i "s/^WEBUI_SECRET_KEY=.*/WEBUI_SECRET_KEY=$(openssl rand -hex 32)/" .env
# Set WEBUI_UID/WEBUI_GID to the user that runs sndbx:
sed -i "s/^WEBUI_UID=.*/WEBUI_UID=$(id -u)/;s/^WEBUI_GID=.*/WEBUI_GID=$(id -g)/" .env
```

Edit `.env` and set `EXTERNAL_API_BASE_URL` to the address of the external
service on the host (a full `http://host:port` URL). Set `EXTERNAL_API_KEY` only
if the service requires a bearer token.

### 3. Register the sandbox in sndbx

Then merge the two blocks from `config.sndbx.json5` into the root
`$SNDBX_ROOT/config.json5`:

- the `"open-webui"` entry under `sandboxes.items`;
- the `"open-webui-env-token"` entry under `envids`.

The template uses `${SNDBX_ROOT}/images/open-webui` directly. Override its
defaults from the root `.env` if needed with `OPEN_WEBUI_HOST_PORT`,
`OPEN_WEBUI_SSH_HOST_PORT`, `OPEN_WEBUI_MEMORY`, `OPEN_WEBUI_CPUS`,
`OPEN_WEBUI_BIND_HOST`, or `OPEN_WEBUI_PORT`. These names deliberately avoid
the root sndbx `WEBUI_PORT`, which configures the administration UI.

### 4. Build the image

sndbx auto-builds a configured local image on first use when it is missing, but
it can also be built explicitly:

```bash
cd "$SNDBX_ROOT/images/open-webui"
docker build -t open-webui:latest .
```

### 5. Load the configuration and start the sandbox

Reload sndbx so it reads the merged configuration, then start the `open-webui`
sandbox from the Web UI dashboard or an MCP tool. To have it start with sndbx,
set `run_at_startup: true` in the merged block.

```bash
# Reload without touching other running sandboxes:
systemctl --user kill --kill-whom=main --signal=SIGKILL sndbx.service || \
  sudo systemctl restart sndbx.service
```

Because the container remaps to `WEBUI_UID` (which you set to the sndbx
runner), data files are owned by that user and no ACL scripts are required for
the sndbx path. `prepare_host_permissions.sh` is only needed for the standalone
Docker Compose workflow or when running under a different identity.

### Optional: SSH access

Add public keys to the sandbox's `ssh_keys` list, then restart or recreate it,
and connect through the published port:

```json5
ssh_keys: [
  "ssh-ed25519 AAAA... operator@example",
],
```

```bash
ssh -p <published-ssh-port> openwebui@127.0.0.1
```

## Connecting to external services

The external service is expected to expose both an OpenAI-compatible API and an
Ollama-compatible API. The launcher sets:

- `OPENAI_API_BASE_URLS=<EXTERNAL_API_BASE_URL>/v1` and `OPENAI_API_KEYS=<EXTERNAL_API_KEY>`
- `OLLAMA_BASE_URL=<EXTERNAL_API_BASE_URL>`

so the service appears under **Settings -> Connections** for either connection
type. Explicit `OPENAI_API_BASE_URLS`, `OPENAI_API_KEYS`, or `OLLAMA_BASE_URL`
values in `.env` override the derived ones.

The VM reaches the external service over the network, so
`EXTERNAL_API_BASE_URL` must be an address the guest can route to (the host's
LAN address by default). The address, port, and any token live only in the
git-ignored `.env`; the tracked `.env.example` keeps placeholders.

Set `EXTERNAL_API_KEY` only when the service requires a bearer token; otherwise
it may be left empty.

## Running with Docker Compose (optional)

Choose either this standalone deployment or the sndbx sandbox for one checkout.
Do not run both against the same `data/` directory: they conflict on the
published ports and can concurrently access the SQLite database.

> **WARNING:** `./install.sh` is only for the standalone Docker Compose mode.
> Do not run it when this checkout is managed by sndbx.

The same image can run outside sndbx:

```bash
cd "$SNDBX_ROOT/images/open-webui"
./install.sh   # creates .env + secret, runs prepare_host_permissions.sh, then deploys
```

Open `http://localhost:<published-ui-port>/`, create the admin account, and use
the preconfigured external-service connection.

## Safety

The service runs as an unprivileged `openwebui` account. `.env`, the
`WEBUI_SECRET_KEY`, and the SQLite database live under `data/` and in `.env`;
both are ignored by Git. Never publish `data/` or `/app/backend/data` as a
whole.

## Updates and backup

To update Open WebUI, change `OPENWEBUI_IMAGE` in the `Dockerfile` (pin a
version tag or digest for reproducibility), rebuild the image, and recreate the
sandbox. Do not run `apt upgrade` inside a running VM.

For a consistent backup, stop the service, then copy `data/` preserving owners,
groups, ACLs, extended attributes, and dotfiles:

```bash
docker compose stop open-webui
rsync -aAX --numeric-ids data/ /backup/open-webui-data/
docker compose up -d
```

If `data/` was copied without metadata, run `sudo ./run_after_restore.sh` before
starting the container.

## Diagnostics

```bash
docker compose ps
docker compose logs -f open-webui
docker compose exec open-webui bash
docker compose down
```

first-run path. `TEST.md` records the verification protocol.
